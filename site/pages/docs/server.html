Your own server, set up in a minute.

  • For running your own server {{name}} runs on your own computer, and that's all most people need. If you'd rather keep it on a server you rent and look after, these setups do the work.
  • Paste it when you create the server On a new Debian or Ubuntu server, put these two lines in the user data field, and pick your SSH key as usual: 
    #!/bin/sh
curl -fsSL {{serverFiles}}/user-data.sh | sh
  • Where the field is DigitalOcean: Advanced options → Add initialization scripts. Hetzner: Cloud config. AWS Lightsail: Add launch script. AWS EC2: Advanced details → User data. Any other host that runs cloud-init has a user data field too.
  • What it does At first boot it adds the user overhand with the SSH keys the host put on the server, installs git, gh and ps, and runs the installer as that user, with linger on, so {{name}} starts at every boot. It opens no port. Read the whole user-data.sh before you paste it. It's done a minute or two after the server boots; /var/log/cloud-init-output.log shows how far it got.
  • Then sign in From your laptop, sign in as overhand with a tunnel, run overhand open there, and open the link it prints in your laptop's browser: 
    ssh -L {{port}}:127.0.0.1:{{port}} overhand@your-server
    Setup then signs your agents in from the app, as Agent sign-ins without a desktop shows.
  • Docker instead On a server that has Docker, the same setup as a compose file, everything on one volume: 
    curl -fsSLO {{serverFiles}}/compose.yml && docker compose up -d
    Then tunnel in as any user and run docker exec overhand overhand open. To update: docker compose pull && docker compose up -d.
  • No deploy button A hosting platform's deploy button puts an app on a public web address, and {{name}} never opens to the internet. A plain server, reached over SSH or your tailnet, keeps it yours.

On a Linux server.

  • The same installer Run the one command from Install over SSH, as the user the agents should work as. The same package runs on arm64 and x64.
  • Kept running With systemd it's a user service, and linger keeps it up after you log out. Without systemd, run overhand start again after each reboot. On Linux has the commands.
  • Only on the server itself {{name}} listens on 127.0.0.1, so nothing outside the server reaches it until you choose one of the ways in below.
  • Check it overhand doctor over SSH lists what's missing: an agent, gh and its sign-in, a place for secrets.

In Docker.

  • The image Each release is published for arm64 and x64 as {{image}}. Run it, or use the compose file above: 
    docker run -d --name overhand --network host --restart unless-stopped \
  -v overhand:/home/overhand {{image}}
    To build it yourself instead, run docker build -t overhand . in a clone of the repository.
  • Host network, loopback only With --network host it listens on the server's own 127.0.0.1, like the plain install. Publishing a port with -p reaches nothing, because inside the container it listens on loopback too. On Docker Desktop the host network is its VM's, so this setup is for a Linux server.
  • One volume It runs as the user overhand, not root. Its home is the volume: {{name}}'s state, the agents you install, their sign-ins, GitHub's login and your projects. API keys go to a file only that user can read.
  • Day to day docker ps shows it healthy once it answers on its port. Run commands with docker exec overhand overhand doctor; its log is docker logs overhand. Another port: -e OVERHAND_PORT=4400.
  • Turning it off and updating Turn off in {{name}} restarts the container; docker stop overhand stops it. To update, docker pull {{image}}, then remove the container and run it again. The volume keeps everything.

Reach it from your laptop or phone.

  • An SSH tunnel From your laptop, then open the link overhand open prints on the server: 
    ssh -N -L 4317:127.0.0.1:4317 you@your-server
  • The same port on both ends {{name}} answers only to the address it serves on, so a tunnel from another local port gets refused.
  • Counts as the server Through the tunnel your browser is the server's own: finish setup and add devices there.
  • Tailscale for your phone On the server, serve {{name}} on your tailnet, then add that https address in Settings → Extra origins: 
    tailscale serve --bg --https=8443 http://127.0.0.1:4317
    A request through it gets nothing until that device is paired: open Settings → Phone through the tunnel and add the device there. See Phone and Access from anywhere.
  • Access from anywhere On Pro and Team, set it up once in Settings → Phone through the tunnel; after that {{relayHost}} reaches the server from any device, with no tunnel and no open port. See How linking works.
  • Never the open internet Don't publish the port or put it behind a public proxy or Tailscale Funnel. The tunnel or your tailnet is the way in.

Agent sign-ins without a desktop.

  • Agent accounts sign in from the app Settings → Agent accounts runs the agent's own sign-in on the server, and its page opens on your laptop or phone. Nothing to run over SSH. See Sign-ins and API keys.
  • Setup shows the command No terminal window can open on a server, so setup shows the exact command to install an agent and sign it in. Run it over SSH; in Docker, inside the container: 
    docker exec -it overhand sh -c '<the command setup shows>'
  • Claude Code, by hand claude auth login prints a link. Open it on your laptop, sign in, and paste the code it gives you back into the terminal.
  • Codex, by hand Plain codex login waits for your browser on the server's own port 1455. Run codex login --device-auth instead, and enter the code it shows on your laptop.
  • GitHub gh auth login --web shows a one-time code; enter it at github.com/login/device on any device.
  • An API key instead Add it in Settings → Agent accounts. With no keyring on the server it goes to OVERHAND_SECRETS_FILE, which the image sets. See Agents and accounts.
