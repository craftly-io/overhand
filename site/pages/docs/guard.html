Checked before it runs.

  • One set of rules Every agent with a hook runs the same guard, set up per run from {{name}}'s own folder. Your own config for each agent stays as it is.
  • What it blocks {{guardBlocks}} The whole list is under the hood.
  • Its own off switch It also blocks changes to {{name}} itself and to an agent's project settings, which could turn the guard off for the next run, even when a ticket asks.
  • It fails closed A guard that can't start blocks the call.
  • Your processes Ports, process names and containers you list in governor.protect can't be stopped or restarted by an agent.

How it reaches each agent.

{{guardTable}}

Each account in Settings → Agent accounts says where its agent stands.

Every pull request also runs the guard on each hooked agent's own hook messages: merges, force pushes, deploys, secret reads, protected edits and ordinary work (guard-conformance.ts; bun run guard-check from a checkout, per installed agent). That proves the guard's side, not that the agent calls its hook: only a real run confirms that.

Everything it blocks.

  • Pushes Force pushes, and pushes to main, master, develop and other shared branches.
  • Pull requests Merging, closing or approving them, by gh or by the API.
  • The GitHub repository itself Its administration, releases and secrets.
  • Going live Deploys, infrastructure changes and package publishing.
  • Secret files Keychain, password and credential files (SSH, cloud) and production env files, by file tool or named in a command.
  • SSH keys Naming an SSH key or ~/.ssh in a command, so no ssh -i ~/.ssh/<key> and no edits to known_hosts or config. A plain git push over SSH still works: it names neither.
  • Data Production databases and destructive SQL.
  • Your disk Deleting your home folder or the root.
  • {{name}} itself Its config folder, config, state, code and heavy-job slots.
  • Agents' project config .gemini/, .codex/, .opencode/, opencode.json, .cursor/hooks.json and cli.json, .aider.conf.yml and .aiderignore. Changing those is yours to do, even when a ticket asks.
  • Modes and quiet It also enforces {{modeWatch}} and quiet mode. See Modes and Quiet mode.
  • A project with its own hooks Codex, Gemini CLI and OpenCode won't start in a project that already carries hook settings or plugins of its own. The run moves on to the next account.
  • The rules One file decides for every agent: packages/core/src/guard.ts.

How each hook is wired.

  • Claude Code A PreToolUse hook on every tool, in {{name}}'s config folder or by --settings.
  • Codex A PreToolUse hook on every tool (shell, apply_patch, and MCP tools, which reach other services) by -c hooks.PreToolUse=…. It passes --dangerously-bypass-hook-trust, since Codex skips hooks nobody reviewed in /hooks and this one is {{name}}'s own. It still runs in its workspace-write sandbox.
  • Gemini CLI A BeforeTool hook on every tool, in the user settings of a Gemini home of {{name}}'s (GEMINI_CLI_HOME). Gemini CLI 0.65 skips a system settings file unless root owns its folder, so a Gemini account runs on its API key. --approval-mode yolo only skips Gemini's prompts; its hooks still run first.
  • Cursor Agent A local plugin (--plugin-dir) whose hooks (beforeShellExecution, beforeReadFile, beforeMCPExecution, preToolUse) call the guard, with failClosed.
  • OpenCode A plugin (tool.execute.before) in a config folder of {{name}}'s (OPENCODE_CONFIG_DIR).
  • Aider No hook to use. It runs with --no-suggest-shell-commands --no-auto-test --no-auto-lint (no shell at all), an empty --config and --env-file /dev/null, so no .aider.conf.yml or AIDER_* in .env turns it back on. An --aiderignore lists the secret files, and it can't open files outside its repo.
  • Set per run Every one of these comes from ~/.overhand/agent-home, run by run. Settings reads each account's line from one table, packages/contract/src/guard.ts.

What it can't do.

  • A program's next step {{guardLimit}}
  • The OS sandbox {{sandboxStops}}
  • What the sandbox can't stop {{sandboxLimit}}
  • Turning it on Settings, Agent accounts: off, log only or on (sandbox.mode in the config). It's sandbox-exec on macOS and bubblewrap on Linux. Log only (macOS) runs as before and writes what it would block to logs/sandbox-would-deny.jsonl. A change applies to runs started after it, so a running lead keeps going. Under it, Codex's, Gemini CLI's and Cursor Agent's own sandboxes are off: macOS can't nest them.
  • A project without it {{sandboxProjectOff}}
  • So keep tokens small Give agent accounts credentials that can't do damage anyway: no admin or deploy rights, and branch protection on your GitHub repositories.
  • See what it stopped Guardrails, in Health, lists each attempt it blocked in the last day, with its time and rule.
